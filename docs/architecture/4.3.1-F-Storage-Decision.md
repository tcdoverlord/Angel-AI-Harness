# 4.3.1-F Storage Decision Record

## Decision
**Option B: ConversationStore retained; SQLite remains canonical and receives operational improvements.**

## Evidence
- Existing relational schema already represents conversation relationships and derived summaries.
- 100, 1,000, and 5,000 message temporary databases passed SQLite integrity checks.
- Retrieval of up to 1,000 messages remained measurable at 0.653 ms, 7.971 ms, and 9.744 ms respectively in the benchmark environment.
- A 1,000-message database was copied using SQLite's online backup API and restored with all 1,000 messages intact.
- Startup/schema initialization remained approximately 0.88–1.22 ms in the benchmark environment.

## Why not per-conversation JSON?
No measured SQLite limitation currently justifies introducing a second canonical storage system. JSON would need to reproduce relationships, recovery semantics, and consistency guarantees already supplied by SQLite.

## Why not retire compatibility JSON immediately?
Retirement is a separate migration decision. The current JSON artifact is no longer authoritative, but keeping it as compatibility/export-only avoids an unnecessary breaking change while the export/import and recovery contract can be validated independently.

## Reversibility
`ConversationStore` remains the application boundary. A future storage implementation can be introduced behind that boundary without rewriting conversation consumers.
